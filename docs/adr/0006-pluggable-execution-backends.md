# ADR-0006: Pluggable execution backends; local Docker first; cloud hosting is approval-gated

**Status:** Accepted (2026-10-30).

**Context:** ADR-0003 and ADR-0004 describe the hosted target as two restricted AWS Fargate tasks per run. No AWS account resources or other paid cloud services are authorized for this project at present. The runner, shadow previews, verification, investigation, reproduction, GitHub integration, dashboard and benchmark do not depend on AWS in principle, and coupling the supervisor to ECS APIs would make the product untestable on a laptop and in CI and would fix the hosting choice before its cost is known.

**Decision:**

1. **One interface for execution.** The supervisor creates, uses and destroys run environments only through an execution-backend interface: provision a role-scoped environment (reference or candidate) from a digest-pinned image, deliver a digest-verified source artifact, run a bounded step, expose the environment's database to trusted services only, list resources by run, destroy them, and report observed resource use. Run state, leases, retries, verification, evidence and reporting never call a backend-specific API.
2. **Local Docker is the first backend.** For each run and role it creates a separate internal Docker network with no route to the internet or the host; containers from digest-pinned images, with all capabilities dropped, `no-new-privileges`, non-root users and memory, CPU and process limits; run-scoped labels that cleanup and the expiry reconciler use to find every resource; and no GitHub, cloud or model credentials. PostgreSQL is reachable by trusted host-side services only through a port bound to the loopback interface; the candidate and reference networks cannot reach each other or that port.
3. **Local Docker is a trusted-development backend.** The operator's Docker daemon is part of the trusted computing base, and containers share a kernel, so local isolation is weaker than separate virtual machines. It is the boundary for development, CI and the local demo, not for a public hosted service. Its controls are tested, not assumed.
4. **No cloud backend is provisioned.** Before any cloud deployment the maintainer presents the owner with: a cost estimate built from measured local resource use (task CPU, memory, build time and run duration, issue #5) and the provider's current prices; the security implications, including how each hosted-only control in THREAT_MODEL would be met; and the lowest-cost viable hosting options. Nothing is provisioned without the owner's explicit approval. Until then, no document or README may claim a cloud deployment, and the AWS sections of ARCHITECTURE, THREAT_MODEL and ADR-0004 describe a proposed hosted target, not existing infrastructure.
5. **Hosted-only controls keep their meaning.** No task IAM role, VPC-endpoint-bound pre-signed source URLs and an EventBridge-scheduled reconciler remain requirements for an AWS backend. Their local equivalents are: the trusted supervisor copies the source artifact into the container before start, and the image's trusted entrypoint verifies its SHA-256 before any PR code runs; and an expiry reconciler that runs as a process separate from the API and removes expired resources by label.

**Why:** Keeps every product capability buildable and testable now, at no cost, while leaving the hosted target a deliberate, priced decision rather than an accident of early coupling.

**Alternatives rejected:** (1) Call ECS `RunTask` from the supervisor and mock it locally, which leaves isolation untested; (2) run migrations and candidate code in the supervisor process during local development, which removes the boundary the product depends on; (3) provision free-tier cloud resources without approval, since free tiers expire and still create billing exposure.

**Consequences:** The product contract is unchanged: the restricted hosted demo (work package 11, gate G5) is deferred until approved, not dropped, and the release checklist items that need it stay open. A cloud backend is an additional implementation of the same interface and must pass the same isolation tests plus the hosted-only ones. Local Docker cannot demonstrate VM-level isolation, and reports from it say which backend ran.
