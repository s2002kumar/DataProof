# ADR-0008: Invariants C4 to C8, what is built and what the claim is narrowed to

**Status:** Accepted (2026-11-04).

**Context:** `SCENARIO_CONTRACT` names eight invariants. C1 to C3 and C6 are protected oracles and have been verified live and on the benchmark. C4 (relationships), C5 (temporal semantics), C7 (reprocessing) and C8 (schema) were specified but not built as contracts, and `STATUS` has listed them as a shortfall since the first release review. The owner asked for each to be examined on its own, for the meaningful checks to be built with real fault and clean-control tests, and for any claim that stays unsupported to be narrowed explicitly rather than implied.

**Decision, invariant by invariant:**

1. **C8, schema: built as the type check.** A data comparison proves only what the fixture exercises: a money column declared `numeric(12, 0)` passes a fixture of whole-unit amounts and rounds the first real refund; a `timestamp without time zone` column holds no instant. `type_check` (`packages/verifier/column_types.py`) judges what PostgreSQL declared the candidate's result columns to be, from the same query the data check ran: `DECIMAL` needs `numeric` with a declared scale at least the contract's (or an integer type when the scale is zero), `INSTANT` needs `timestamp with time zone`, and floating-point types never qualify. It is its own check, `types.<contract>`, required when the contract is. **Not built:** the rest of C8's text, "candidate ledger PK/FK/uniqueness": a result column is not traceable to its table column through the wire protocol, so declared uniqueness and foreign keys are not read from the catalog. Duplicate keys are still caught at run time (`ERROR: DUPLICATE_KEY`), and a binding that reads through an expression carries no declared scale, so only its type family is judged. The claim is therefore: **C8 is the type fitness of every compared column, not a constraint audit.**
2. **C7, reprocessing: built as the rerun check, in the Action.** `migration.rerun` runs `alembic upgrade head` a second time on the migrated candidate and requires the step to succeed and every table to digest exactly as before. This is C7's literal statement (a completed revision is not applied again, which Alembic's version table guarantees) plus what it does not say: work done outside the revision mechanism, in `env.py` or by a revision Alembic did not record, changes the digest and blocks. Retry *effects* that happen inside a single revision (an insert run twice) remain data faults, which C1 and C2 catch (benchmark family "retry effects", 2 of 2). **Not built:** the rerun check in the App's pipeline; and "interrupted/non-transactional revision semantics are reported explicitly" is not implemented beyond Alembic's per-revision transaction, which the sample app and the example use. The claim is narrowed to: **a second upgrade is a no-op, verified by the Action; the App's pipeline does not yet run it.**
3. **C4, relationships: established by C1, not by a separate contract.** C1 compares every event's `order_id` with the reference's, keyed by event ID, and reports keys the candidate adds or loses; the reference's own referential integrity is enforced by its foreign keys. So a ledger row pointing at an order that does not exist, or at another customer's order, is a C1 mismatch (benchmark family "orphaned reference", 2 of 2, and the subscriptions `plan-catalog-orphans` case through `subscription_state`). **Not built:** a general relational invariant ("every target row references a real parent") that a maintainer could declare without a keyed oracle. The claim is narrowed to: **relationships are verified where an oracle carries the reference column, which the demo and example oracles do; there is no standalone relationship contract.**
4. **C5, temporal semantics: established by the `INSTANT` comparator and the type check.** Instants are compared as instants with their offset pinned, so representation differences never fail and shifts always do (benchmark family "timestamp shift", 2 of 2; the subscriptions `period-session-timezone` case, 374 of 374 instants); the fixtures place periods across daylight-saving transitions in several zones; and the type check refuses a column that cannot hold an instant. **Not built:** a per-contract precision or tolerance policy for timestamps (only `DECIMAL` has a tolerance) and any wall-clock-preserving mode. The claim is narrowed to: **exact instant preservation, nothing weaker and nothing else.**

**The schema diff (#6).** A schema-only comparator was listed as a benchmark baseline. By construction it reports DDL differences, which every change set in both corpora has (a new table, new columns), and it cannot see values, so it cannot separate the faults from the clean controls at the data level; the type check above is the part of a schema comparison that bears on correctness, and it is evaluated against the contract rather than against the reference schema. The named tool, `migra` 3.0.1663481299 (last released in 2022), installs but fails to import on Python 3.12 (`pkg_resources`); running it needs Python 3.11, `setuptools` and `psycopg2`, which this environment did not permit. It has therefore **not been run**, and no number is claimed for it; the comparator stays listed as not run, with the structural argument above in place of a result.

**Why not more:** a constraint audit, a relational-invariant language or a timestamp policy would each be a new verification feature with its own trust questions (a PR-supplied invariant is a binding and needs the same review). None is needed to support the released claims once those claims say what the oracles do.

**Consequences:** `PRODUCT`'s capability list and `STATUS` requirement 5 say exactly this. The Action runs eight required checks on the subscriptions example (execute, rerun, three contracts, three type checks). The App's pipeline gains the type and rerun checks in a later change that also regenerates the pipeline-tier results, so that the committed results stay what the code produces.
