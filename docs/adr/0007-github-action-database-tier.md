# ADR-0007: A GitHub Action for the database tier, beside the GitHub App

**Status:** Accepted (2026-11-04).

**Context:** The GitHub App (ADR-0003 to ADR-0006) gives a full review: previews of both commits, API behaviour checks, AI roles, reproduction and interactive binding approval. It needs a control plane, a worker, a dashboard and an App registration, which is more than a repository needs to get the one thing most migrations lack: a verdict on the data after the migration ran. A GitHub Action can give that verdict inside the repository's own CI with nothing to host. It must not be a shortcut around the App's safety model: an Alembic migration is arbitrary Python, and a job that runs it holds a token and may hold secrets.

**Decision:**

1. **Scope.** The Action verifies the database tier only: the pull request's migration against the protected data contracts, in disposable reference and candidate PostgreSQL databases. API behaviour contracts (C6), previews, the AI Change Analyst and Failure Investigator, reproduction and interactive approval stay with the App. The Action says so in every job summary. An API oracle in the Action's oracle directory is `NOT_RUN: UNSUPPORTED`, which makes the run `INCOMPLETE`, never green.
2. **Reuse.** The Action is `packages/action` over the existing verifier, contracts, local Docker backend and trusted entrypoint. It has no verification logic of its own: `verify_contract`, `assemble_contract`, `derive_verdict` and the rule-based diagnosis are the App's. The job summary is the App's check summary (`packages/report`).
3. **Trusted inputs come from the base branch's tip.** The repository-owned configuration (`dataproof/config.toml`), the fixture, the oracles, the pinned requirements of `env.py` and the binding approvals are read from the base branch as it is when the job runs, straight from git objects, never from the checkout's working tree. The pull request's head commit contributes only its migrations (as a `git archive`) and its proposed bindings. A pull request that edits a trusted file sees the edit ignored and listed in the summary; it takes effect once merged.
4. **Approval is a reviewed change to the base branch.** A binding is approved when its content digest (`binding_approval_digest`: contract ID, query, route and mapping; not the commit or path) is in `approved_bindings` on the base branch. Until then every check that depends on it is `NOT_RUN: AWAITING_BINDING_REVIEW`, the run is `INCOMPLETE` and the job fails. The summary shows what the binding reads, flags relations the pull request did not create or alter, and names the digest to add. There is no approval by label, comment or re-run: those are grantable by people without write access to the base branch, and the App's digest-bound interactive approval needs the App.
5. **Isolation of the migration.** The migration runs in a step container of the local Docker backend, exactly as in the App: a migration image built in the job from the base branch's inputs (the trusted entrypoint verifies the source archive's SHA-256 as an unprivileged user before `alembic upgrade`), on an internal network whose only other member is its own PostgreSQL container, with every capability dropped, `no-new-privileges`, a non-root user, memory, CPU and process limits, a tmpfs workspace and a timeout. Its environment holds the disposable database's URL and nothing else: no `GITHUB_TOKEN`, no runner token, no secret, no Docker socket, no runner filesystem, no `.git` directory. The database role it migrates with cannot create roles or databases. This holds for pull requests from forks too; a read-only token is not what protects the job.
6. **The event.** The Action runs on `pull_request` and refuses `pull_request_target`, which would hand the migration a write-capable token and the repository's secrets. The recommended workflow has `permissions: contents: read`. Fork pull requests run under the same isolation; a repository that prefers not to run them sets `policy.forks = "refuse"` on the base branch and gets `NOT_EXECUTED: FORK_PULL_REQUEST`.
7. **Outcome.** The job's exit code is zero only for `CHECKED` and `CHECKED_WITH_WARNINGS`. `BLOCKED` is 1, `INCOMPLETE` 2, `NOT_EXECUTED` 3, and an infrastructure or configuration failure (no Docker, the base branch's own migrations fail, the fixture does not load) is 4 and not a verdict. The summary carries the verdict, the next step, bounded expected-versus-observed examples, the coverage tally with unsupported checks named, the evidence digests, the rule-based diagnosis, the bindings awaiting review, the trusted files the pull request changed, and the digests the run was pinned to. Annotations point failing checks at the migration files the pull request changed. Both databases are dumped by trusted code into the report directory.

**Why this and not a lighter design:** running the migration in the job's own process, or in a container with the workspace mounted, would expose the token in `.git/config`, the runner's environment and the Docker socket to arbitrary Python from the pull request. Reading the configuration from the checkout would let a pull request approve its own binding or relax its own oracle. Approving by label or comment would move the decision outside branch protection.

**What the Action cannot prevent, and says so:**

- A `pull_request` workflow runs the workflow file from the pull request's merge, so a pull request can edit or remove the job that calls the Action. Branch protection with the job as a required status check blocks a removed job (the check never reports) but not a job rewritten to pass. The repository must protect `.github/workflows/` and `dataproof/` with code-owner review, or require the workflow through a ruleset. The Action documents this; it cannot enforce it.
- Containers share the runner's kernel. GitHub-hosted runners are single-use virtual machines, so a kernel escape yields that machine and the job's read-only token; on a self-hosted runner it yields whatever that runner holds. Do not run untrusted pull requests on a persistent self-hosted runner.
- Resource exhaustion is bounded, not prevented: a hostile migration can spend the step's CPU, memory and time until the timeout.
- The migration image's extra requirements are installed from the base branch's file with network access at build time, before any pull-request code exists in the job. A compromised dependency there is the repository's trusted supply chain, as it is for the migrations themselves after merge.

**Alternatives rejected:** `pull_request_target` with a checkout of the head (the standard mistake); `services: postgres` with the migration in the job process (no isolation from the token); a hosted DataProof endpoint called from CI (that is the App); approval by pull request label or by a maintainer's re-run (not bound to the base branch).

**Consequences:** two integrations share one verification engine and one report; the Action's security claims are tested by adversarial migrations (`tests/integration/test_action.py`: credential, network, Docker-socket and workspace probes, self-approval and oracle-weakening attempts, a dropped table, a no-op migration, a hang, `pull_request_target`, fork policy, and cleanup). No version tag is published until the security tests pass in CI, a clean installation from the pinned commit has produced genuine results on a fresh repository, and the owner approves; the checks are listed in [ACTION_SECURITY_REVIEW.md](../ACTION_SECURITY_REVIEW.md). No external adoption is claimed until someone other than the author has run it.

**Amendment (2026-11-07): output channels.** Text a pull request controls (binding contents and the errors that quote them, file names, relation names its migration creates) reaches the job log, workflow commands and the summary only escaped: on one line with `::` broken, or as escaped Markdown. An invalid binding could otherwise forge a workflow command such as a passing notice (found in the release review; fixed and tested).
