# The Action's release security review

The checks run before the Action gets a version tag, and what each one found. The design is [ADR-0007](adr/0007-github-action-database-tier.md); the threat it answers is that an Alembic migration is arbitrary Python, written by whoever opened the pull request, running inside a job that holds a token. Reviewed 2026-11-07 against commit `e2f91b06` and the changes in the pull request that adds this document.

| Area | What was checked | How | Result |
| --- | --- | --- | --- |
| Credential isolation | What the pull request's code can reach: the job's token and secrets, the runner's environment, the Docker socket, the workspace and its `.git`, the network, DNS, the host gateway, a superuser role | A hostile migration probes each one from inside the step, with canary secrets in the job (`test_a_hostile_migration_reaches_no_secret_network_socket_or_workspace`) | Every probe denied. Its environment holds only `DATABASE_URL` and Python settings. The canaries reach no migration, report or summary |
| Untrusted Alembic code | Where the pull request's Python runs: `versions/`, and also its `env.py` and its `alembic.ini` at the configured path, which come from the head commit too | Code reading; the rerun check runs `upgrade head` twice; an `env.py` that writes on every run is caught (`test_work_outside_the_revisions_fails_the_rerun_check`) | All of it runs only in the step container. The Action's own process never imports pull-request code. The base branch's migrations run from the base commit's archive |
| Step variables | What `alembic.environment` lets into a migration step | Unit tests of the rules on both sides (`tests/unit/test_step_variables.py`); an `env.py` that builds its URL from its own settings is `BLOCKED` without them and `CHECKED` with them, and the database password appears in its output only as `[REDACTED]` (`test_an_env_py_that_reads_its_own_settings_needs_them_from_the_base_branch`) | Declared on the base branch only, like the rest of the configuration. Names DataProof sets (`DATABASE_URL`, `PATH`, `HOME`, `LANG`, Python's settings, `DATAPROOF_*`) are refused where they are declared and again by the trusted entrypoint. Placeholders resolve only to the disposable database. A literal value is public text in the repository: the documentation says never to put a real secret there, and the Action cannot tell |
| Trusted base-branch inputs | Whether a pull request can change what it is held to: configuration, oracles, fixture, requirements, binding approvals | The head commit approves its own binding, replaces an oracle and empties the fixture (`test_a_pull_request_cannot_approve_its_own_binding_or_weaken_an_oracle`) | None of the three counts. Each is read from the base branch's tip through git objects, and each edit is listed in the summary |
| Output channels | Whether text the pull request controls can become a workflow command, a forged annotation, or Markdown/HTML in the summary. That text includes binding contents, and so the errors about them, file names, and relation names its migration creates | Adversarial tests (`test_a_binding_cannot_forge_workflow_commands_through_an_error`, `test_a_contract_id_cannot_forge_a_line_of_its_own`); code reading of every log line, command and summary section | **Found and fixed.** An invalid binding's error quoted its TOML keys, unescaped, on lines of their own. A key such as `::notice title=DataProof CHECKED::…` became a forged notice in the job log. The error now reaches logs and commands on one escaped line, with `::` broken, and the summary escaped. Binding paths, relation names and changed-file paths in the summary are escaped too |
| File listing | Whether an odd file name in the bindings directory (a newline, quotes, a symbolic link) can be misread | Code reading | **Found and fixed.** The listing now uses `git ls-tree -z` and takes regular files only |
| Verdicts and exit codes | That the job is green only for `CHECKED` and `CHECKED_WITH_WARNINGS`, and that every other outcome is distinct | Tests for each: `CHECKED` (0), `CHECKED_WITH_WARNINGS` from an optional contract that errors (0), `BLOCKED` (1), `INCOMPLETE` from an unapproved binding and from an unsupported API contract (2), `NOT_EXECUTED` for a refused fork (3), and `ERROR` for `pull_request_target`, an invalid binding and a malformed base configuration (4) | As designed. A required check that did not run, including one the Action does not support, is never success |
| Skipped tests | Whether a required CI job can be green while something it was meant to prove did not run | CI logs: `python-tests` reported `747 passed, 1 skipped` (the browser test, which the `e2e` job runs) | **Hardened.** With `DATAPROOF_FORBID_SKIPS=1`, set in every test job, a skip fails the run. `python-tests` no longer collects the browser test |
| Workflow permissions | Event, token scope, credentials left in the checkout | The quickstart and example workflows; the Action's code | `pull_request` only (`pull_request_target` is refused), `permissions: contents: read`, `persist-credentials: false`. The Action makes no GitHub API call and reads no token. Fork pull requests run under the same isolation |
| Artifact contents | What the report directory holds, since workflows upload it | Code reading of `report.json` and the dumps | `report.json` holds verdicts, at most 20 mismatch examples per check, query and result digests, and each step's output: at most 16 KB, written by the pull request's code, with database passwords redacted. `reference.dump` and `candidate.dump` are `pg_dump` archives of the two fixture databases. Everything is derived from the fixture, which must hold no real data. Shorten the artifact's `retention-days` if the default 90 days is too long |
| Supply chain | What the Action installs and from where | `action.yml`, `uv.lock`, the migration image's Dockerfile | The Action's Python environment comes from `uv.lock` (`uv sync --frozen`, hashes verified). Third-party actions are pinned by commit, and images by digest. The migration image installs pinned versions of Alembic, SQLAlchemy and psycopg, plus the base branch's requirements file, **without hashes**: a limitation, not a finding, since PyPI does not replace a published file, but hash pinning is not enforced |
| Docker and the runner | What happens on the runner itself | ADR-0007 | Containers share the runner's kernel. On a GitHub-hosted runner (a single-use VM), an escape yields that VM and a read-only token. On a persistent self-hosted runner it yields the runner: do not run untrusted pull requests on one |
| The workflow file | Whether a pull request can bypass the check | ADR-0007 | It can rewrite or delete the workflow in its own merge. The controls are the repository's: make the job a required check, and require code-owner review for `.github/workflows/` and `dataproof/` (the example repository ships a `CODEOWNERS` for this). The Action cannot enforce them |

## What is required before a tag

1. Every row above holds on the release commit, with CI green on `action-tests`, which is now a required check on `main`, as is `dataproof`.
2. A clean installation from the pinned commit on a fresh repository and runner, with genuine results. This exists: [dataproof-example-subscriptions](https://github.com/s2002kumar/dataproof-example-subscriptions), recorded in [ACTION_FIELD_RESULTS.md](ACTION_FIELD_RESULTS.md).
3. The owner's explicit approval to publish the tag.

Use by someone other than the author (#80) is not a precondition for the tag. It is the precondition for any claim of external adoption, and no such claim is made until it happens.
