# THREAT MODEL — Untrusted Code, SQL, AI, GitHub and Cloud

## Assumptions and assets

The repo content, SQL, pull-request body, migration comments and AI tool-visible text are untrusted. The public reviewer UI may be reachable from the internet. Important assets: GitHub installation credentials, cloud IAM, execution host, non-sensitive fixture databases, preview URLs, evidence files, internal control-plane DB, LLM API key and billing budget. No real production secrets or personal data in demo baselines.

## Threat-to-control map

| Threat | Primary controls | Verification gate |
| --- | --- | --- |
| Malicious PR changes `Dockerfile`, dependency manifests or lockfiles | Immutable runtime digest, `allowed_change_roots`, protected configuration; unapproved dependency/runtime changes → `NOT_EXECUTED: DEPENDENCY_CHANGE_REQUIRES_IMAGE_APPROVAL` | PR changing Dockerfile or lockfile is rejected before task creation |
| Candidate Python/Next source performs hostile commands during import/build | Source executes/compiles only inside untrusted task with **no task IAM role**, no NAT/egress, no GitHub/LLM keys, restricted ephemeral DB privileges, bounded CPU/disk/TTL; never on API host | Attempted network egress, host access, and secret discovery all denied |
| SQL exfiltration or cross-run network access | Isolated per-run tasks/networks, restricted egress and IAM, disposable DB credentials, no production connections | External network/other-run DB access denied in tests |
| Container breakout / resource exhaustion | Separate reference and candidate Fargate tasks; CPU/memory/disk/time caps, nonroot processes, no privileged mode/ECS Exec; **independent EventBridge scheduled** TTL reconciler kills tasks even if API is down | Resource exhaustion, API-down orphan cleanup and separation tests |
| Prompt injection in SQL/comments/evidence | Treat content as data; allowlisted diagnostic tools; deterministic policy middleware; output schema validation | Injected instruction cannot change run state, perform write or change verdict |
| PR-supplied candidate binding reads unchanged legacy data (directly, through a new view or inside a function) so oracles pass while the new schema is wrong | Binding relations AST-extracted and resolved through views; relations the PR did not create or alter are flagged for the reviewer; user-defined functions rejected; human `APPROVE_BINDING`, with approver ≠ PR author when the repository has more than one maintainer (ADR-0005) | Binding reading `legacy_payment_events` directly or through a new view is flagged; bindings using user-defined functions or operators, `query_to_xml` (even inside a PR-created view) or system catalogs are rejected; author self-approval rejected in a multi-maintainer repository |
| Forged GitHub event or stale PR commit | Verify HMAC signature/install/repo, idempotent delivery, exact SHA binding, supersession cancellation | Tampered event rejected; old run cannot approve new SHA |
| Evidence tampering / stale artifacts | Content-addressed/sealed manifests, run-specific prefixes, atomic commit, no read of previous run artifacts | Cross-run evidence/stale-run test |
| Hidden data leak in logs/reports/LLM | Redact credentials and high-risk fields; bounded samples; private artifacts, prompt data minimization | Secret canary absent from output and traces |
| Preview gateway accepts external address (SSRF/open proxy) | Trusted supervisor registers task private IP/port; signed expiring token bound to run+role; gateway rejects all client-supplied upstream hosts; API-check routes in oracles and PR bindings are validated local paths (no scheme, host, `//` or `..`) sent only to the run's own preview | Attempted internal URL, unregistered task or stale token denied. *Implemented in [`services/api`](../services/api/README.md#signed-preview-gateway); negative tests in `tests/integration/test_preview_gateway.py` (#4).* |
| Preview URL unauthorized access | Auth gateway, expiration, token binding to run, private network for backend/DB | Unauthorized requester denied |
| Untrusted preview code acts as the reviewer | A preview runs the pull request's frontend code. It is served only from its own host (`<role>-<run>.<preview domain>`, a separate registrable domain from the dashboard), never from the dashboard's origin, so it cannot read the reviewer's session or CSRF token. Grant cookies are host-only, the dashboard's writes require its own `Origin` and CSRF token, and no cookie a preview sets reaches the browser | A preview's own host cannot use the dashboard session; a write from a preview origin is refused |
| AI-generated SQL migration fix unsafe | Suggestion only; human review before new SHA/correction; deterministic replay in fresh environment | No model-controlled production or auto-merge path |
| Cost abuse / abandoned environments | Hard supervisor concurrency limit, rate limits, AWS Budgets **alarm (not a hard cloud spend stop)**, capped task runtime, independent TTL reconciler | Expired tasks cleaned, alerts verified; measured peak spend tracked. *Local: the independent reaper (`python -m dataproof_api reaper`) removes expired environments from Docker labels alone, with no database or secret, and journals them (`tests/integration/test_reaper.py`). The investigator's budget caps tool calls, turns and cost.* |

## Trusted boundaries

1. GitHub input -> authenticated control API.
2. Control API -> durable supervisor/job broker.
3. Supervisor -> **untrusted isolated execution plane**. Trusted broker fetches exact GitHub SHA and verifies source digest; candidate runs no unapproved Dockerfile or dependencies; it has no task IAM role, installation token, control-plane DB credential or AWS admin token. Each migrator has only a non-superuser owner role limited to its disposable DB (no `COPY FROM PROGRAM`, `pg_read_file`, `lo_import`, untrusted extensions); read queries use a separate least-privileged role. Execution-role permissions for ECR/logs remain outside task code. The task's only S3 access is one pre-signed, VPC-endpoint-bound GET for its run's source artifact; every write, including `pg_dump` evidence, is made by the trusted broker. Port 5432 on each task admits only the supervisor, verifier and broker, and PostgreSQL superuser credentials stay in the sidecar container (ADR-0004).
4. Evidence store -> AI investigator. Model receives bounded/redacted data; typed tools are **exactly** `get_check_result(id)`, `get_evidence(id)`, `get_schema(env, table)`, `read_source(path, start, end)` (pinned head SHA, **allowlisted application/migration source paths only**; never `benchmarks/`, hidden labels, `docs/`, or test fixture labels), `run_readonly_query(env, sql, max_rows)`. SQL is AST-validated (single permitted `SELECT`/`WITH`, disallow write-CTEs and `COPY`, `pg_read_*`, `lo_*`, `dblink`, `postgres_fdw`); a separate database read-only role, `default_transaction_read_only=on`, statement timeout, restricted `work_mem`, max rows and **max result bytes** supply defense in depth. Every contract or diagnostic query is sent as a prepared statement (extended protocol): under the simple query protocol a single string such as `SELECT …; COMMIT; DELETE …` ends a read-only transaction and runs the write, which was confirmed against PostgreSQL 17 and is covered by verifier tests. Each model output must cite actual evidence IDs and is schema-validated; tool/token budgets and pinned model/prompt versions recorded. LLM key is held in investigator service only. *Implemented: the five tools, PostgreSQL-backed query validation (shared with bindings), row, byte and time caps, citation validation and injection negatives are in [`packages/investigator`](../packages/investigator/README.md); no paid model is called without owner approval.*
5. Reviewer -> signed/authenticated preview and report. No bypass through raw public container ports.

## Cloud deployment restriction

A public service that builds/runs arbitrary GitHub repositories cannot be considered secure simply because Docker is present. Fork PRs are `NOT_EXECUTED`. Private preview ingress is restricted to authenticated run-bound gateway; AWS private subnets have no NAT and allowed VPC endpoint policies are scoped to project resources. Each environment (reference/candidate) is a distinct task and cannot see the other task database. Runtime dependencies are protected/pinned; a Next.js source change is compiled offline inside the isolated task, never on the control plane. GitHub App asks only `checks:write`, `contents:read`, `pull_requests:read`, `metadata:read` permissions and verifies installation/repo scope. The committed project is a **restricted configured-repository integration and allowlisted public demo**. Broad public multi-tenant execution is out of product scope. AWS task-sidecar isolation, image provenance, exact permissions and cost/rate controls must be demonstrated, not just documented.

## Local execution backend

Local Docker (ADR-0006) is a trusted-development backend. Per run and role it uses a separate internal network with no route to the internet, the host or the other role, digest-pinned images, dropped capabilities, `no-new-privileges`, non-root users, resource limits, run-scoped labels and loopback-only database ports, and every one of these controls has a negative test (`tests/integration/test_local_docker.py`, described in the [runner README](../services/runner/README.md#tested-isolation)). It cannot provide VM-level isolation: containers share the host kernel and the operator's Docker daemon is trusted. Passing local tests does not demonstrate the hosted-only controls above, and no report or document may present it as the hosted boundary.

## The GitHub Action

The Action ([ADR-0007](adr/0007-github-action-database-tier.md), [docs/ACTION.md](ACTION.md)) runs inside a repository's own GitHub Actions job, which holds a `GITHUB_TOKEN` and may hold secrets, and executes the pull request's Alembic migration, which is arbitrary Python. It uses the local Docker backend above as its boundary: the migration runs in a step container with no credential, no network but its own database, no Docker socket and no runner filesystem, from a `git archive` whose digest the trusted entrypoint verifies. Its trusted inputs (configuration, fixture, oracles, requirements, binding approvals) are read from the base branch's tip, so a pull request cannot approve its own binding or weaken what it is held to. It runs on `pull_request` only and refuses `pull_request_target`. What it cannot prevent is stated in the ADR: a pull request editing the workflow that calls it (branch protection and code-owner review on `.github/workflows/` and `dataproof/` are the control), a kernel escape on a shared or persistent runner, and resource use up to the step's limits. Its adversarial tests are listed below; the local backend's limits apply to it unchanged.

## Mandatory security tests

For the Action: a hostile migration's credential, network, DNS, Docker-socket, workspace and superuser probes all denied; the job's canary secrets absent from every migration, report and summary; a pull request's edits to the configuration, the fixture and an oracle ignored and listed; an unapproved binding failing closed; a dropped table, a no-op migration behind an approved binding and a hang all `BLOCKED`; `pull_request_target` refused before Docker; fork policy; an invalid binding or a contract ID unable to forge a workflow command or summary content; an optional failure giving `CHECKED_WITH_WARNINGS`, an unsupported API contract giving `INCOMPLETE`, and a malformed base configuration giving `ERROR`, never success; nothing left behind (`tests/integration/test_action.py`; the release review is [ACTION_SECURITY_REVIEW.md](ACTION_SECURITY_REVIEW.md)).

For the App: webhook forgery, stale SHA, injected AI instructions, `DROP`/`COPY`/extension abuse attempts, lockfile/Dockerfile changes denied, malicious app-build/import egress attempt, source-digest mismatch, cross-run and cross-task DB access, unauthorized signed gateway proxy targets, resource exhaustion, API-down orphan cleanup, task timeout/cancel, replay retry, reference-oracle violation, legacy-relation binding flagging, binding self-approval, fail-before-cleanup, evidence-scope bleed and preview-token expiry. Any unmitigated critical escape or secret exposure blocks cloud launch.
