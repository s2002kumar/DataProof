### `case-121`: lossy numeric conversion (one decimal place)

- **Model-off:** COMPLETED; root cause no; named 0 of 384 affected events; 7 of 7 citations exist; 0 of 3 specifics unsupported; 0 tool calls; 0 in / 0 out tokens; 0 USD; 0.842 ms.
  - commerce.c1_event_preservation: Values differ in ways these rules do not recognize.
  - commerce.c2_refund_totals: Values differ in ways these rules do not recognize.
  - commerce.c3_capture_totals: Values differ in ways these rules do not recognize.
- **Model:** COMPLETED; root cause yes; named 0 of 384 affected events; 14 of 14 citations exist; 0 of 16 specifics unsupported; 12 tool calls; 55143 in / 2168 out tokens; 0.1120130 USD; 23079 ms.
  - The likely root cause is the new ledger_entries.amount column. In CANDIDATE it is NUMERIC(18,1), but the source column legacy_payment_events.amount in REFERENCE is NUMERIC(18,2). When the migration copied the data, PostgreSQL rounded every amount to one decimal place. In the c1 mismatch examples, 49.99 became 50.0, 10.01 became 10.0 and 602.87 became 602.9. My query found that exactly 384 of the 435 reference amounts have a non-zero second decimal digit. That matches c1's 384 mismatches exactly. No rows were lost (435 keys on both sides), and no amount rounded down to zero.
  - The c2 (refund totals) and c3 (capture totals) failures follow from the same rounding. Each per-order, per-currency total in CANDIDATE adds up the already-rounded ledger amounts, so it differs from the REFERENCE total by small rounding amounts. For example, a refund total of 49.99 became 50.00, a capture total of 1586.49 became 1586.50, and 9876543210.99 became 9876543211.00. The c2 precondition (no order refunded more than it captured) returned 0 rows in REFERENCE, so that does not explain the c2 failure.
  - Declare ledger_entries.amount as NUMERIC(18,2) or wider, to match legacy_payment_events.amount. Then re-run the migration and backfill so amounts copy without rounding, and re-run c1–c3.
