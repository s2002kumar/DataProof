# Subscriptions: an example repository for the DataProof Action

A second application profile, designed independently of the commerce scenario: plans, customers, subscriptions and invoices whose amounts are stored as integer cents. It is what a repository looks like when it uses the [DataProof Action](../../docs/ACTION.md), and what the Action's tests run against.

| Path | What it is |
| --- | --- |
| `alembic.ini`, `migrations/` | The Alembic project. `env.py` takes the database URL from `DATABASE_URL`. `versions/0001_base.py` is the base schema. |
| `dataproof/config.toml` | The Action's configuration, read from the base branch. |
| `dataproof/fixture.sql` | 30 customers, 45 subscriptions and 187 invoices, generated by `scripts/make_fixture.py` from a fixed seed. Fictional. It holds what a cents-to-money migration must get right: amounts whose cents are not whole currency units (1, 99, 1999, 123456), zero tax, billing periods across daylight-saving transitions in several zones, paused and cancelled subscriptions, unpaid invoices and invoices without an external reference. |
| `dataproof/oracles/` | Three protected contracts: every invoice's amounts to the cent (`invoice_amounts`, which states the intended transformation from cents to decimal money), every invoice's billing-period instants (`billing_periods`, with a reference-first precondition), and every subscription's customer, plan, state, seats, discount and instants (`subscription_state`). |
| `changes/` | Twelve change sets, each a pull request against the base schema: three clean controls and nine faults, listed below. |

A standalone repository holds the first four rows at its root and gets the change sets as pull requests. The Action's tests build exactly that from this directory ([`tests/subscriptions_env.py`](../../tests/subscriptions_env.py)); [`tests/integration/test_subscriptions_scenarios.py`](../../tests/integration/test_subscriptions_scenarios.py) verifies every change set at the database tier with the counts the fixture makes deterministic.

## Change sets

**Sourced** means the fault's pattern comes from a publicly documented incident or bug report, linked in the table; the implementation on this schema, and the evaluation of whether DataProof catches it, are ours. **Authored** means pattern and implementation are both ours. Every migration here executes without error on PostgreSQL 17.

| Change set | Origin | What the migration does | Outcome |
| --- | --- | --- | --- |
| `money-columns` | authored (clean) | Replaces the cents columns with `numeric(12, 2)` money columns, `subtotal_cents::numeric / 100`, with a binding for the new columns | `CHECKED` |
| `invoice-index-and-comment` | authored (clean) | A partial index and a table comment; no data changes | `CHECKED` |
| `plan-catalog` | authored (clean) | Splits `plans` into `plan_catalog` with decimal prices and moves the foreign key; a binding reads the plan code from the catalog | `CHECKED` |
| `money-columns-truncated` | authored | The money conversion with integer division: `subtotal_cents / 100`, so 19.99 becomes 19.00 | `BLOCKED`: `invoice_amounts` fails on every invoice with cents |
| `money-columns-float-roundtrip` | sourced: [brd.mn, "Floating Point Arithmetic and Why It Makes Cents"](https://brd.mn/articles/floating-point/) (a payment-file conversion that truncated cents: 389 transactions, 3.89 short) | The conversion is correct, then totals are "normalized" through `trunc(float8 * 100) / 100`; `19.99 * 100` is `1998.9999999999998` | `BLOCKED`: `invoice_amounts` fails on the 15 totals whose float product lands below the integer, each exactly one cent short |
| `period-session-timezone` | sourced: [exasol/database-migration#72](https://github.com/exasol/database-migration/pull/72) (instants written as a session's wall clock, "no error, and CHECK_MIGRATION reports OK"); [google/adk-python#6396](https://github.com/google/adk-python/pull/6396) (naive local timestamps relabelled as UTC) | Converts the period columns to `timestamp` under `Europe/Berlin` and back to `timestamptz` under UTC | `BLOCKED`: `billing_periods` fails on both instants of all 187 invoices |
| `tax-rates-fanout` | sourced: PostgreSQL's [`UPDATE ... FROM` caveat](https://www.postgresql.org/docs/current/sql-update.html) and [pgsql-general, 2013](https://postgresql.org/message-id/52A08E1C.1010702%40volny.cz) (a join matching more than one row makes the row used unpredictable); [rails/rails#47895](https://github.com/rails/rails/issues/47895) (batched iteration through a has-one that matches several rows skips records) | Adds a rate table with two rows for one region and recomputes tax by summing over the join, so tax doubles; the deterministic form of the fan-out | `BLOCKED`: `invoice_amounts` fails on `tax` and `total` |
| `backfill-batches-skip-first` | sourced: [GitLab !224446](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/224446) and [#590848](https://gitlab.com/gitlab-org/gitlab/-/issues/590848) (batched migrations marked finished without running), [GitLab !255692](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/255692) (a filter in the wrong place excluded valid records from a copy) | Backfills the money columns in windows of `(start, start + 50]`, so the first invoice is never converted; the new columns were left nullable | `BLOCKED`: `invoice_amounts` fails on the first invoice's three columns, `NULL` observed |
| `paid-at-sentinel` | sourced: [woocommerce/woocommerce#68772](https://github.com/woocommerce/woocommerce/pull/68772) and [#68866](https://github.com/woocommerce/woocommerce/pull/68866) (a zero date copied as "no date", and dates the migration did not copy, later overwritten with the current time) | Writes `1970-01-01` into `paid_at` where it is `NULL`, then makes the column `NOT NULL` | `BLOCKED`: `billing_periods` fails on `paid_at` for the 38 unpaid invoices |
| `plan-catalog-orphans` | sourced: [home-assistant/core#91117](https://github.com/home-assistant/core/issues/91117) (a table split that left 212,920,276 rows with a `NULL` reference to the new table) | The `plan-catalog` split with a filter that drops the free plan; subscriptions on it get a `NULL` plan | `BLOCKED`: `subscription_state` fails on `plan_code` (`free` expected, `NULL` observed) for every subscription on the free plan |
| `invoices-copied-positionally` | sourced: [dbt-labs/dbt-adapters#1511](https://github.com/dbt-labs/dbt-adapters/issues/1511) (`insert ... select *` maps columns by position), [dimitri/pgloader#132](https://github.com/dimitri/pgloader/issues/132) (values swapped between columns on load) | Rebuilds `invoices` with `tax_cents` before `subtotal_cents` and copies rows with `SELECT *`; the total check still holds | `BLOCKED`: `invoice_amounts` fails on `subtotal` and `tax` for the 151 invoices where they differ |
| `import-not-idempotent` | sourced: [strapi/strapi#27567](https://github.com/strapi/strapi/issues/27567) (an internal migration without a guard, run twice by two instances, duplicated ~2,800 documents) | Imports invoices from a staging copy twice, guarded by `external_ref = ...`, which never matches a `NULL` reference | `BLOCKED`: `invoice_amounts` and `billing_periods` fail with twice the unreferenced invoices as extra keys |

What these show, and what they do not: each fault is observed by an oracle that declares the invariant it breaks. A fault no oracle declares would pass, exactly as the two NULL-and-empty cases do in the [commerce benchmark](../../benchmarks/results/REPORT.md). The sourced incidents are evidence that these fault shapes happen in production software that passed its own tests; they are not evidence about how often, and the re-implementations here are small by construction.
